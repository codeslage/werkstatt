## Technischer Ansatz

Wie in Phase 1 läuft nichts auf einem eigenen Server (ADR 0009). Die Plattform besteht aus vier Teilen:

1. **CWK-Quelle in `werkstatt`:** Ein Manifest `cwk/manifest.json` listet jede Datei des CodeslageWerkzeugKastens: Quelle in `werkstatt`, Ziel im Projekt-Repo, Teil (Regel oder Code), Art (exakt oder ergänzbar). Die Prüfungen sind **wiederverwendbare GitHub-Workflows** (`cwk-rules.yml`, `cwk-code.yml`). Projekt-Repos rufen sie über einen auf einen Commit gepinnten Verweis auf. `werkstatt` nutzt dieselben Workflows selbst, so dass die Prüfungen nicht auseinanderlaufen (AK-3). Einziger Pflicht-Check im Ruleset ist der Sammel-Job `ci-ok`. Neue Jobs im CWK brauchen deshalb keine Änderung an den Rulesets der Projekte.
2. **Vorlage und Anlegen:** `codeslage/project-template` ist ein öffentliches GitHub-Template-Repo mit dem CWK und einer minimalen Beispiel-App. Der Befehl `pnpm cwk new` legt ein Repo aus der Vorlage an. Er schreibt die Festlegungen in `cwk.json`, setzt die Rulesets und die Sperrliste und startet die erste CI (AK-1 bis AK-6).
3. **Betrieb im privaten Repo `codeslage/platform`:** Sync, Übersicht mit Erinnerung, zentraler Historien-Scan und Portal-Build laufen als GitHub-Workflows in einem **privaten** Repo. Ihre Logs nennen private Repo-Namen und Inhalte; in `werkstatt` wären sie öffentlich. Für den Zugriff gibt es zwei **GitHub Apps**. `codeslage-cwk-read` darf nur lesen und ist für alle Repos installiert. Sie bildet die Soll-Menge, sammelt Doku ein und scannt die Historie. `codeslage-cwk` darf schreiben (Sync-Branches und PRs) und ist **nur für öffentliche Projekt-Repos** installiert, also nicht für `werkstatt` (die CWK-Quelle) und für kein privates Repo. Dort könnte GitHub Free die Freigabe nicht erzwingen (P1). Die Freigabe eines Sync-PR erzwingt **GitHub selbst** über ein Ruleset: Nötig ist ein Code-Owner-Review des Teams `@codeslage/maintainers`, bezogen auf den neuesten Push. Eine App kann nicht Mitglied eines Teams sein und steht auf keiner Bypass-Liste. Sie kann einen Sync-PR deshalb nicht mergen, auch wenn sie Workflow-Dateien ändern darf (AK-8, AK-19).

   **CWK-Release:** Eine gemergte Änderung am CWK in `werkstatt` ist wie ein Release auf der Ebene darüber: Sie wird in die Projekte ausgerollt. In öffentliche Repos rollt der Sync automatisch per PR aus. In private Repos (`platform`, `internal`, private Kundenprojekte) rollt der Inhaber selbst aus, mit `pnpm cwk sync --private` und seinem gh-Login. Das legt in jedem privaten Repo einen Sync-PR an. Liegt ein privates Repo 14 Tage hinter dem neuesten Stand, kommt eine Mail (P1, P5).

4. **Docs-Portal als zwei statische Sites** auf Cloudflare Pages, gebaut mit Astro Starlight:
   - `docs.codeslage.de` enthält **nur** öffentliche Doku.
   - `docs-internal.codeslage.de` enthält alles und liegt mit allen Adressen hinter **Cloudflare Access**. Zugang haben nur Mail-Adressen auf einer Liste; die Anmeldung läuft über einen Einmal-Code per Mail.

   Weil die beiden Sites getrennt gebaut werden, kann interne Doku weder über Suche noch über den Seitenindex noch über direkte Adressen der öffentlichen Site sichtbar werden (AK-13). Aktualisiert wird so: Ein Organisations-Webhook meldet jeden Push an einen kleinen **Cloudflare Worker**. Der prüft die Signatur und startet den Build bzw. den Sync in `platform` (AK-7, AK-12). Nächtliche Läufe für Sync und Portal fangen verlorene Webhooks ab.

Fehler melden sich wie in Phase 1: Ein fehlgeschlagener Workflow-Lauf erzeugt eine GitHub-Mail an den Inhaber (AK-16, AK-22, AK-26). Damit die Mail ankommt, gilt (Protokoll T-41): Geplante Läufe liegen nur in `platform`, und ihre Cron-Zeilen ändert nur der Inhaber. Läufe, die der Webhook startet, löst ein Token des Inhabers aus, der Inhaber ist also Auslöser. Infrastruktur bei Cloudflare (Pages-Projekte, DNS, Access, Worker) kommt per OpenTofu in `infra/tofu/live` dazu (ADR 0002). GitHub-Einstellungen richtet `cwk new` per `gh` ein; der Rest steht im Runbook (AK-21).

`codeslage/internal` bekommt eine `cwk.json` mit „ohne Code“ und `"docs": "none"` und wird im letzten Schritt angebunden. Laut Frage 5 erscheint es nicht im Portal.

Das Team ist damit Code-Owner aller Dateien. `cwk new` gibt ihm in jedem Repo ausdrücklich Schreibrecht, sonst erkennt GitHub es nicht als Code-Owner an.

## Datenmodell & Schnittstellen

**`cwk/manifest.json` (in `werkstatt`)**, beim Lesen gegen ein Schema geprüft (Artikel VII):

```json
{
  "files": [
    { "source": "CONSTITUTION.md", "target": "CONSTITUTION.md", "part": "rules", "mode": "exact" },
    { "source": "cwk/files/CLAUDE.md", "target": "CLAUDE.md", "part": "rules", "mode": "extendable" },
    {
      "source": "cwk/files/.github/workflows/ci.yml",
      "target": ".github/workflows/ci.yml",
      "part": "rules",
      "mode": "extendable"
    },
    { "source": "packages/config/eslint.config.js", "target": "eslint.config.js", "part": "code", "mode": "exact" }
  ]
}
```

- `part`: `rules` | `code`. `mode`: `exact` (muss Byte für Byte dem gepinnten Stand entsprechen) | `extendable` (muss außerhalb eines Projektblocks übereinstimmen).
- Projektblock in Markdown: `<!-- cwk:project:start -->` … `<!-- cwk:project:end -->`; in YAML: `# cwk:project:start` … `# cwk:project:end`. Je Datei höchstens ein Block, sein Inhalt gehört dem Projekt.
- **Platzhalter `@CWK_REF`:** In Quelldateien steht statt des gepinnten Commits `@CWK_REF`, z. B. `uses: codeslage/werkstatt/.github/workflows/cwk-rules.yml@CWK_REF`. Der Sync ersetzt ihn durch den SHA, den er auch in `cwk.json` schreibt. `cwk check` vergleicht nach derselben Ersetzung und wird rot, wenn ein `uses:`-Verweis auf `werkstatt` nicht genau auf `cwk.json`.`cwk` zeigt (AK-9).
- Für den schreibenden Sync-Test (AK-7) gibt es je Teil eine Probe-Datei (`.cwk/probe.md`, `.cwk/probe-code.md`), deren Änderung keinen Prozess berührt.
- Der Regel-Teil umfasst Constitution, `docs/prozess/*`, `specs/_vorlagen/*`, `.claude/commands/*` und `.claude/agents/code-reviewer.md`. Dazu kommen die CLAUDE.md-Basis, das PR-Template, `CODEOWNERS`, `.githooks/pre-commit`, die Basis der cspell- und der Prettier-Konfiguration, die `ci.yml` der Projekte und `.env.example`. Den Code-Teil bilden die Konfigurationen aus `packages/config`, `.dependency-cruiser.json`, `knip.json` und das `Dockerfile`-Gerüst. Die genaue Liste entsteht in Schritt 1 und wird dort getestet.

**`cwk.json` (je Projekt-Repo)**, ebenfalls gegen ein Schema geprüft:

```json
{ "cwk": "<Commit-SHA von werkstatt>", "code": true, "docs": "public" }
```

- `cwk`: Stand des CWK, auf dem das Repo ist (AK-9, AK-10). Der Sync setzt ihn, das Projekt ändert ihn nicht von Hand.
- `code`: `true` (Standard) | `false` = „ohne Code“ (AK-1, AK-7, AK-27).
- `docs`: `public` | `internal` | `none`. Fehlt der Wert, gilt `internal` bei privaten und `public` bei öffentlichen Repos (AK-14). Ein öffentliches Repo kann nicht `internal` sein, weil seine Doku auf GitHub ohnehin öffentlich ist; `cwk check` lehnt das ab.
- Fehlt `cwk.json` in einem Repo der Organisation (außer `werkstatt`), ist das ein Fehler: Der Sync-Lauf wird rot, die Übersicht zeigt das Repo als „nicht angebunden“ (AK-7, Soll-Menge).

**Rulesets je öffentlichem Projekt-Repo** (gesetzt von `cwk new`, geprüft vom Job „Repo-Einstellungen“):

| Ruleset         | Regeln für `main`                                                                                                                                                          | Bypass                                                                  |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `main-checks`   | nur per PR, kein Force-Push, kein Löschen, Pflicht-Check `ci-ok`, festgelegt auf die Quelle GitHub Actions (damit keine andere App einen gleichnamigen Status setzen kann) | keiner                                                                  |
| `main-approval` | 1 Approval, Code-Owner-Review, veraltete Freigaben werden bei neuem Push verworfen, Freigabe des neuesten Pushes nötig                                                     | Rolle „Repository admin“, Modus „nur für PRs“ (eigene PRs des Inhabers) |

Damit kann der Inhaber eigene PRs wie bisher nach grüner CI mergen. Ein Sync-PR der App braucht dagegen sein Code-Owner-Review zum aktuellen Stand (AK-8). Kommt nach der Freigabe ein neuer Sync-Commit, verfällt die Freigabe (AK-25). `werkstatt` bekommt ebenfalls `main-approval`, dazu `CODEOWNERS` mit `* @codeslage/maintainers` und Schreibrecht für das Team. So kommt auch eine Änderung an der CWK-Quelle nur mit Freigabe des Teams auf `main`, nicht mit dem Approval einer beliebigen App. Für eigene PRs des Inhabers ändert sich dadurch nichts (Bypass). Ob die Kombination wie gedacht wirkt, prüft Schritt 2 am Probe-Repo, **bevor** die App Rechte bekommt.

**Sammel-Job `ci-ok`:** läuft mit `if: always()` und `needs:` auf alle Jobs. Er ist rot, sobald ein Job `failure` oder `cancelled` meldet. `skipped` ist nur bei den Jobs aus `cwk-code.yml` erlaubt und nur, wenn `cwk.json` `"code": false` sagt. Sonst wäre ein übersprungener `ci-ok` bei einem Fehler davor für GitHub „erfüllt“.

**Sync-PR im Detail (AK-25):** Gibt es den Branch `cwk/sync` schon, setzt der Sync darauf auf und legt einen neuen Commit an. So bleiben eigene Commits des Inhabers auf dem Branch erhalten. In ergänzbaren Dateien bleibt der Projektblock aus dem Stand des Branches stehen. Die PR-Beschreibung nennt den alten und den neuen CWK-Stand und verlinkt die Änderungen in `werkstatt`.

**Erinnerung (AK-26):** `cwk status` ist rot und erzeugt damit eine Mail, wenn ein Sync-PR mindestens 14 Kalendertage offen ist und seit der letzten Erinnerung mindestens 7 Kalendertage vergangen sind. Den Zeitpunkt der letzten Erinnerung hält die Schreib-App als Kommentar im PR fest („Erinnerung gesendet am …“), in privaten Repos `cwk status` mit dem Token der Lese-App nicht, deshalb steht der Zeitpunkt dort in `platform/reminders.json`, geschrieben vom `GITHUB_TOKEN` des Laufs. So ist er sichtbar und übersteht ausgefallene oder verspätete Läufe. Für private Repos, in denen kein automatischer Sync-PR entsteht, wird `cwk status` rot, sobald eines mindestens 14 Tage hinter dem neuesten CWK-Stand liegt und kein Sync-PR offen ist.

**Prüfung von außen (AK-9):** `cwk check` in der CI prüft mit den Workflow-Dateien des PR-Branches, also mit Code, den derselbe PR ändern kann. Deshalb führt `cwk status` jede Nacht in `platform` den aktuellen `cwk check` aus `werkstatt/main` gegen `main` jedes Repos aus. Rot wird er, wenn ein Repo z. B. außerhalb des Projektblocks den Aufruf von `cwk-code.yml` entfernt hat oder einen Pin auf einen Commit außerhalb von `werkstatt/main` setzt (etwa aus einem Fork).

**Webhook → Worker (AK-7, AK-12):** Der Organisations-Webhook schickt das Ereignis `push` an `https://docs-trigger.codeslage.de`. Der Worker:

1. prüft `X-Hub-Signature-256` mit HMAC-SHA256 und lehnt bei Fehler mit 401 ab;
2. prüft die Nutzdaten gegen ein Schema und liest nur `ref`, `repository.full_name` und die Pfade in `commits[].added/modified/removed`;
3. tut nichts, wenn der Push nicht `main` betrifft oder keine relevanten Pfade berührt: Doku (`docs/`, `specs/`, `cwk.json`) bzw. bei `werkstatt` die Pfade aus dem Manifest;
4. startet sonst per `workflow_dispatch` `portal.yml` bzw. `sync.yml` in `platform`.

Der Worker protokolliert keine Nutzdaten, nur Ergebnis und Repo-Name bei Ablehnung (Artikel XVI, keine personenbezogenen Daten). Ungültiges wird abgelehnt, nicht repariert (Artikel VII).

## Schritte (je ein PR)

### Schritt 1 – CWK-Quelle und Prüfungen in `werkstatt`

Zuerst die Tests, dann `cwk/manifest.json` mit vollständiger Liste und `tools/cwk check` mit Schema-Prüfung, Projektblöcken und `@CWK_REF`. `cwk-rules.yml` und `cwk-code.yml` werden wiederverwendbare Workflows, `cwk-code.yml` mit bedingten IaC-Prüfungen. `ci.yml` von `werkstatt` ruft beide auf und hat den Sammel-Job `ci-ok`; `repo.test.ts` und das Ruleset von `werkstatt` werden auf `ci-ok` umgestellt. `werkstatt` hat danach dieselben Prüfungen wie vorher, nur anders aufgerufen; der Vergleich der CI-Läufe vorher/nachher wird protokolliert.
**AK:** AK-3 (Aufbau), AK-9 (Logik).

### Schritt 2 – Vorlage, `cwk new`, Rulesets

V1 durch den Inhaber. `werkstatt` bekommt `CODEOWNERS` (`* @codeslage/maintainers`), Schreibrecht für das Team und das Ruleset `main-approval`; „Repo-Einstellungen“ prüft das auch in `werkstatt`. `codeslage/project-template` anlegen: CWK-Dateien, minimale App mit `/health`, Test, Dockerfile, `cwk.json`, `CODEOWNERS`. Dazu `cwk new` und `cwk secrets` mit Tests (die gh-Aufrufe liegen hinter einer kleinen Schnittstelle, damit Tests sie ersetzen können) und das Runbook `docs/runbooks/neues-projekt.md`. Probelauf: `cwk-sample` und `cwk-sample-no-code` anlegen, Zeit nach Systemuhr messen. Am öffentlichen Probe-Repo werden die Rulesets geprüft: Eigener PR des Inhabers lässt sich mergen; ein PR eines anderen Kontos ohne Code-Owner-Review nicht, **auch nicht mit dem Approval eines Nicht-Owners**; nach einem neuen Push verfällt die Freigabe; ein fehlgeschlagener Job macht `ci-ok` rot.
**AK:** AK-1, AK-2, AK-3 (Nachweis), AK-4, AK-5, AK-6, AK-27 (CI ohne Code).

### Schritt 3 – `platform`, GitHub App und Sync

`platform` über `cwk new --private --no-code`. V2 durch den Inhaber. `sync.yml` mit `cwk sync`, manuell, per Dispatch und nächtlich. Probe-Änderung je Teil, Sync-PRs gegen die Soll-Menge zählen. Zwei Änderungen nacheinander ergeben einen PR. Eine eigene Änderung auf dem Branch bleibt erhalten. Ohne Code-Owner-Review ist kein Merge möglich, auch nicht per App-API. Die Schreib-App hat in `werkstatt` und in privaten Repos keinen Zugriff (per API geprüft). In private Repos rollt der Inhaber mit `cwk sync --private` aus; liegt eines 14 Tage zurück, kommt eine Mail (P1, P5).
**AK:** AK-7, AK-8, AK-19 (App-Rechte), AK-25, AK-27 (Sync nur Regel-Teil).

### Schritt 4 – Übersicht, Erinnerung, zentraler Historien-Scan

`cwk status` mit Tests: Die Uhr ist ein Parameter, geprüft werden die Tage 13, 14, 20 und 21 sowie verschobene Uhrzeiten und ausgefallene Läufe. Dazu kommen die Prüfung von außen (Fälle „CI-Datei entkernt“ und „Pin aus Fork“), der Abgleich der Soll-Menge (ein öffentliches Projekt-Repo ohne Installation der Schreib-App oder ein privates mit Installation macht den Lauf rot) und der Rückstand privater Repos. In `platform` laufen `status.yml` (nächtlich: Übersicht und Erinnerung) und `history.yml` (monatlich: gitleaks und Sperrliste über die Historie aller Projekt-Repos; `werkstatt` hat seinen eigenen Scan). Beide haben den Eingang `simulate_failure` wie in Phase 1. Fehler werden provoziert, der Mail-Eingang protokolliert. Weil `platform` jeden Monat die Historie jedes Projekt-Repos scannt, gilt AK-22 zentral. Ein Scan im Projekt-Repo selbst würde seine Fehler-Mail an die App schicken (Risiko „Mail-Empfänger“). AK-22 ist dazu in der Spec angepasst.
**AK:** AK-10, AK-22, AK-26, AK-16 (Teil Sync).

### Schritt 5 – Öffentliches Docs-Portal

`apps/docs` (Starlight), `cwk collect`, `portal.yml` in `platform`: einsammeln → Öffentlich-Scan über den gesammelten Inhalt (bei einem Fund Abbruch vor dem Upload) → Build → Upload; dazu ein nächtlicher Lauf. In Tofu: Pages-Projekt `docs`, Domain `docs.codeslage.de`, DNS. Tests: Erreichbarkeit, Inhalt je Repo, `internal` fehlt, Kanarienbegriff verhindert die Veröffentlichung.
**AK:** AK-11, AK-15, AK-23, AK-18 (Teil).

### Schritt 6 – Internes Portal mit Access

Pages-Projekt `docs-internal`, Domain `docs-internal.codeslage.de`. Access-Anwendungen für die Domain **und** die `pages.dev`-Adresse samt Vorschau-Adressen. Die `pages.dev`-Adresse kommt in Tofu aus dem Attribut `subdomain` des Pages-Projekts, nicht von Hand; der Test liest dieselbe Quelle. Policy „Mail-Adresse in Liste“. Die Liste ist eine Tofu-Variable aus `.env`, nicht im Repo. Die Übersicht aus Schritt 4 erscheint als interne Seite. Tests ohne Anmeldung: Startseite, tiefe Seite, Suchindex, Sitemap, `pages.dev`- und Vorschau-Adresse werden umgeleitet oder abgelehnt. Die öffentliche Site enthält den Kanarien-Inhalt aus `cwk-sample-no-code` nicht. Manuell: Test-Adresse freischalten, lesen, entfernen, abgelehnt. Einträge in `docs/dsgvo.md`: Access und Workers.
**AK:** AK-13, AK-14, AK-24, AK-20.

### Schritt 7 – Aktualisierung per Webhook

`apps/docs-trigger` (Worker) mit Tests: gültige und ungültige Signatur, fremde Branches, Pfade ohne Doku, CWK-Pfade in `werkstatt`, ungültige Nutzdaten, keine Nutzdaten im Log. Tofu: Worker, Route, Secrets. V6 durch den Inhaber. Infra-Test `docs-freshness.test.ts`: pusht eine Probe-Änderung in die Doku von `cwk-sample`, fragt `docs.codeslage.de` ab und ist rot, wenn sie nach 15 Minuten nicht da ist. Ein provozierter Fehler im Portal-Build erzeugt eine Mail.
**AK:** AK-12, AK-16 (Teil Portal).

### Schritt 8 – Anbindung `internal`, Kosten, Register, Runbooks

`codeslage/internal` mit `cwk.json` („ohne Code“, `docs: none`) anbinden, erster Sync-PR. Danach `docs/kosten.md`, `docs/secrets.md` (App, Tokens, Webhook-Secret, `PUBLIC_BLOCKLIST` je Repo) und `docs/dsgvo.md` prüfen und die Runbooks `neues-projekt.md`, `cwk-sync.md` (Sperrliste ändern → `cwk secrets`) und `docs-portal.md` (Zugang erteilen und entziehen) schreiben. Abgleich wie T-42.
**AK:** AK-18, AK-19, AK-20, AK-21, AK-27 (echtes Repo).

## Risiken

- **Private Repos ohne Schutz (GitHub Free):** Rulesets gibt es auf GitHub Free nur für öffentliche Repos. In privaten Repos (`platform`, `internal`, private Kundenprojekte) ist AK-4 technisch nicht durchsetzbar. Entscheidung P1: Dort gibt es keine Schreib-App und keinen automatischen Sync. Der Inhaber rollt per Hand aus, und eine nächtliche Prüfung meldet Commits auf `main`, die nicht aus einem PR stammen.
- **Ruleset-Kombination ungetestet:** Ob „Code-Owner-Review mit Bypass für Admins nur bei PRs“ zusammen mit dem zweiten Ruleset ohne Bypass genau so wirkt, wie hier beschrieben, ist noch nicht ausprobiert. Schritt 2 prüft das am Probe-Repo, bevor die App Rechte bekommt. Wirkt es nicht, geht es zurück in diesen Plan.
- **Andere Apps mit Schreibrecht:** Die Claude GitHub App hat Schreibrechte in der Organisation. Ihr Review zählt nicht als Code-Owner-Review, weil Apps nicht Mitglied des Teams sein können. Das gilt aber nur, wenn `CODEOWNERS` gültig ist (Team sichtbar, mit Schreibrecht). Der Test in Schritt 2 prüft das mit dem Approval eines Nicht-Owners.
- **Schreibende Workflows auf fremden Branches:** Mit Contents und Workflows Write kann die Schreib-App auf einem Branch eine eigene Workflow-Datei mit `on: push` anlegen. Ein solcher Lauf bekommt alle Repo-Secrets, die nicht an eine geschützte Environment gebunden sind. Regel deshalb: Secrets für Deployments und andere wertvolle Zugänge liegen in Environments, die auf `main` beschränkt sind, nie als Repo-Secrets. Die Regel steht im Runbook `neues-projekt.md` und in `docs/secrets.md`. `PUBLIC_BLOCKLIST` bleibt ein Repo-Secret, weil die PR-Prüfung sie braucht. Ihr Inhalt ist vertraulich, aber kein Zugang.
- **Claude GitHub App in `platform`:** Die Claude GitHub App hat Schreibrechte in allen Repos der Organisation (Entscheidung vom 2026-11-18), also auch im ungeschützten `platform`. Über sie ließe sich die Ersatzprüfung oder eine Cron-Zeile ändern. Entscheidung: P1.
- **Private Repos ohne Schreib-App:** Die Schreib-App ist in keinem privaten Repo installiert. Sie kann deshalb weder die Ersatzprüfung und die Cron-Zeilen in `platform` ändern noch direkt auf `main` privater Repos pushen. Den Preis zahlt die Automatik: Sync-PRs für private Repos stößt der Inhaber an (P5).
- **Mail-Empfänger:** GitHub benachrichtigt bei geplanten Läufen das Konto, das die Cron-Zeile zuletzt geändert hat, bei gestarteten Läufen den Auslöser (Protokoll T-41). Deshalb gibt es geplante Läufe nur in `platform`, und der Webhook startet Läufe mit einem Token des Inhabers (V6).
- **GitHub-Cron ist unpünktlich:** Für AK-12 deshalb der Webhook statt Cron. Die Erinnerung rechnet in Kalendertagen und merkt sich die letzte Mail; sie verträgt verspätete und ausgefallene Läufe.
- **Verlorene Webhooks:** Kommt ein Webhook nicht an, gilt die 15-Minuten-Grenze aus AK-12 bis zum nächtlichen Lauf nicht. Der Sync holt verpasste CWK-Änderungen nachts nach. Die Zustellungen stehen im Webhook-Protokoll von GitHub; das Runbook verweist darauf.
- **Sperrliste veraltet in Projekten:** Ändert sich `.sperrliste`, muss der Inhaber `cwk secrets` ausführen. Die Übersicht zeigt je Repo, wann das Secret zuletzt gesetzt wurde; das Runbook nennt den Schritt.
- **Actions-Minuten in `platform`:** Private Repos haben 2.000 Minuten im Monat frei. Die Schätzung liegt unter 300 Minuten: Builds je Doku-Merge (~2 min), nächtlicher Sync, Build und Übersicht, monatlicher Historien-Scan. Die Kostenübersicht prüft das (AK-18).
- **Werkzeug-Versionen in Projekten:** Die Konfigurationen kommen per Sync, die Versionen von ESLint, Prettier usw. stehen aber in der `package.json` des Projekts. Dependabot hält sie aktuell. Passt eine synchronisierte Konfiguration nicht zur Version, fällt das in der CI des Sync-PRs auf.
