# Protokoll T-10: Schutz von `main` und Secret für die Sperrliste

> Datum: 2026-11-06 · Task: T-10 · AK: AK-1, AK-24 · Repo: `codeslage/werkstatt`

## Ablauf

1. Ruleset `main-schutz` per API angelegt, Status aktiv, Ziel ist der Standard-Branch:
   - Löschen und Force-Push sind verboten.
   - Änderungen nur per PR. Die PR-Regel verlangt 0 Freigaben, weil es nur einen Beteiligten gibt; geprüft wird nach `code-review.md`.
   - Der Status-Check „Secret- und Öffentlich-Scan“ ist Pflicht.
   - Es gibt keine Ausnahmen (`bypass_actors` ist leer).
2. Gegenprobe ohne Login: `GET /repos/codeslage/werkstatt/rules/branches/main` liefert alle vier Regeln. Der AK-1-Test (T-20) kann also ohne Token laufen.
3. Erster CI-Lauf nach dem Push, noch ohne Secret: **rot** mit „Sperrliste fehlt (PUBLIC_BLOCKLIST bzw. .sperrliste), Abbruch.“ Die CI läuft also ohne Sperrliste nicht durch.
4. Der Inhaber hat das Secret `PUBLIC_BLOCKLIST` aus `.sperrliste` gesetzt (`cmd /c "gh secret set … < .sperrliste"`; in Windows PowerShell 5.1 würden Umlaute über die Pipe verloren gehen).
5. Neustart des CI-Laufs: **grün**. Alle Schritte erfolgreich, darunter die Tests des Scans unter Linux und der Historien-Scan mit Sperrliste.
6. Direkter Push eines Commits auf `main`: **abgelehnt** („push declined due to repository rule violations“). Der Commit ist danach über einen Feature-Branch und PR gegangen.

## Ergebnis

✅ `main` ist geschützt, die CI-Ebene des Öffentlich-Scans ist mit Sperrliste aktiv.
